## Configuração OpenNext versionada em 04/10

O primeiro deploy usou a configuração automática efêmera do Wrangler. O repositório agora fixa `@opennextjs/cloudflare@1.20.8`, `wrangler@4.147.0` e `esbuild@0.27.0` no `package-lock.json`, `wrangler.jsonc` com o nome existente `comercio360`, `open-next.config.ts` e scripts em `package.json`. `IMAGES` continua declarado no Worker; a presença do binding não prova o contrato da capa. `public/_headers` dá cache imutável somente aos assets versionados de `/_next/static/*`.

Em **Worker > Settings > Build** da conexão Git com `main`, a raiz do repositório e os comandos **Build** `npm run build:cloudflare` e **Deploy** `npm run deploy:cloudflare` foram conferidos no painel em 04/10. As etapas compartilham o diretório de build: a primeira gera `.open-next`, e a segunda executa somente `wrangler deploy --keep-vars`, sem repetir o build. `--keep-vars` preserva variáveis e segredos de runtime registrados no painel. O padrão `npx wrangler deploy` isolado não executa o build OpenNext depois que a configuração explícita existe. Ainda falta confirmar o próximo build Linux e o hash de `main` publicado.

`NEXT_PUBLIC_SUPABASE_URL` e `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` foram conferidos em **Build variables and secrets** e **Settings > Variables & Secrets** em 04/10 para `comercio360-dev`. `CATALOG_IMAGE_ATTESTATION_KEY` foi enviado somente ao secret do Worker web por script; o banco confirmou o desafio HMAC e a presença do nome do secret foi verificada, mas o upload HTTPS ainda precisa provar o valor no runtime. Não registrar segredos no Git. A [documentação de variáveis do OpenNext](https://opennext.js.org/cloudflare/howtos/env-vars) distingue build e runtime; a [configuração de Workers Builds](https://developers.cloudflare.com/workers/ci-cd/builds/configuration/) distingue os comandos e seus ambientes.

`npm run cf:typegen` validou o `wrangler.jsonc` e gerou os tipos locais ignorados pelo Git. `npm run build:cloudflare` no Windows ficou **FAIL antes do build Next**, com erro do adaptador ao resolver o caminho absoluto de `open-next.config.ts` com barras duplicadas. O próprio OpenNext avisa que o suporte Windows não é completo; WSL e Docker não estão instalados nesta máquina. O build Linux do Git será a prova necessária. O primeiro erro local, falta do `esbuild` importado pelo adaptador, foi corrigido com a dependência fixada. Nenhum deploy remoto foi feito por esta configuração.

O endereço HTTP do Worker respondeu `307` para outra URL HTTP antes desta versão. `custom-worker.ts` passa a devolver `308` para o mesmo caminho e query sob HTTPS antes de chamar o handler OpenNext; `assets.run_worker_first=true` faz o redirecionamento cobrir também os assets. Isso consome invocações do Worker no plano Free. O redirecionamento ainda precisa de prova no deploy Git; o teste local não cobre a rede Cloudflare.

## Alvo correto

O aplicativo usa SSR dinâmico, Server Actions, `proxy.ts`, cookies de Auth e route handler de capa. [Cloudflare orienta Workers com vinext para Next.js completo](https://developers.cloudflare.com/workers/framework-guides/web-apps/nextjs/) e [Pages para exportação estática](https://developers.cloudflare.com/pages/framework-guides/nextjs/). Um preset de Pages com `out/` não atende este projeto. O [guia instalado do Next 16](../node_modules/next/dist/docs/01-app/01-getting-started/17-deploying.md) também limita exportação estática quando há funcionalidades de servidor.

O caminho implantado automaticamente usou OpenNext, embora a Cloudflare hoje recomende vinext como padrão. [OpenNext declara suporte geral a Next 16](https://opennext.js.org/cloudflare), mas seu próprio quadro registra que Node middleware ainda não é suportado. A aplicação usa `proxy.ts` para renovação de sessão; a semântica dessa combinação precisa ser exercida em HTTPS. Um [relato aberto do OpenNext](https://github.com/opennextjs/opennextjs-cloudflare/issues/1394) reproduz falha ao empacotar exatamente `sharp@0.35.4` com Next 16.3.x. O fato de um bundle ter sido publicado não prova que a rota que importa `sharp` funcione no Worker.

## Contrato da capa e opção Cloudflare Images

`lib/catalog-image/process.ts` usa `sharp` nativo no Next local. No Worker, `CATALOG_IMAGE_PROCESSOR=cloudflare` seleciona o adaptador `processCatalogImageCloudflare` via `IMAGES`, mantendo JPEG/PNG/WebP estáticos, limite de entrada e saída de 5 MB, no máximo 10.000 px por eixo e 25 MP, correção de orientação, reencodificação e atestação HMAC dos bytes finais antes do Storage privado. Um stub de `sharp`, o upload do original ou um redimensionamento só na entrega violariam esse contrato.

O [Images binding](https://developers.cloudflare.com/images/optimization/binding/) processa **bytes privados** dentro de Workers sem expor URL de origem. `IMAGES.info(stream)` fornece formato, tamanho, largura e altura; `IMAGES.input(stream).output({format, quality, anim:false})` reencoda. O probe isolado `workers/image-probe/` foi executado com `wrangler dev --remote` em 04/10: **8/8 PASS**. Ele usa o mesmo `processCatalogImageCloudflare` da aplicação e verificou JPEG com EXIF removido e rotação 6 por quadrantes, PNG/WebP, rejeição de APNG/WebP animados, largura 10.001 px, JPEG truncado e entrada maior que 5 MB. Não foi feito deploy persistente do probe.

O primeiro probe remoto revelou **FAIL**: o binding reteve EXIF no JPEG, inclusive quando recebeu `metadata: 'none'` (opção não exposta na [tipagem do binding](https://github.com/cloudflare/workerd/blob/main/types/defines/images.d.ts)). O adaptador agora remove estruturalmente APP0–APP15/COM do JPEG reencodado, dados auxiliares privados de PNG e chunks EXIF/XMP/ICC de WebP; confirma formato/dimensões finais. `lib/catalog-image/animation.ts` rejeita APNG/WebP animados antes do binding. O probe posterior **8/8 PASS** incluiu EXIF/XMP/ICC e PNG tEXt/iTXt/zTXt. Os testes direcionados passaram **16/16**. O FAIL inicial permanece como evidência da correção, não foi reclassificado. A fixture ICC usa sRGB; perfis não sRGB extremos ainda não foram ensaiados. [Relatório do probe](../workers/image-probe/RESULTADO_2026-10-04.md).

O binding aceita até 20 MB, mas o limite de produto continuaria 5 MB. [Preços atuais do Images](https://developers.cloudflare.com/images/pricing/): 5.000 transformações únicas/mês incluídas no plano Free; acima disso, novas transformações recebem erro 9422. O plano Paid cobra US$ 0,50 por 1.000 transformações únicas adicionais. `info()` não é cobrado. Uso do binding introduz essa dependência operacional, mesmo mantendo Supabase Storage; é decisão de arquitetura e custo. O [mock local de Wrangler](https://developers.cloudflare.com/images/optimization/binding/#interact-with-your-images-binding-locally) só cobre largura, altura, rotação e formato; a prova de EXIF/orientação exige `wrangler dev --remote` ou um Worker de homologação com fixture sanitizada e comparação dos bytes via `sharp` fora do Worker.

## Gates antes de aprovar publicação

1. Configurar no Worker **somente por canal de segredo/ambiente** `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` e `CATALOG_IMAGE_ATTESTATION_KEY` operacional, sem valores no Git. Confirmar env de build e runtime no adaptador escolhido; não usar `service_role` na web.
2. Resolver o processamento da capa em `workerd` sem alterar as garantias acima. Testar bundle, upload real JPEG com EXIF/orientação, PNG/WebP, animações rejeitadas, dimensões e limites, checksum/atestação e limpeza no Supabase de homologação. Se escolher Images binding, validar cobrança/cota e falhas 9422/serviço.
3. Exercitar em `https://...workers.dev` login, cookie `Secure`, seleção de loja, renovação, logout, Server Actions, Auth revogado, upload/leitura/remoção da capa e RLS. Repetir com domínio final e Auth redirect URL correta. O login em `/login?reason=configuration` só verifica que a página é alcançável.
4. Confirmar hash de `main` publicado, configuração de build persistente e logs. O `#46e09932` é um deploy inicial técnico; eventual redeploy após mudança deve ter sua própria evidência.

**Conclusão:** a compatibilidade da transformação de imagem foi demonstrada no probe remoto, mas a publicação funcional permanece em gate até o build Linux, a sessão HTTPS e o upload real com Auth/Storage/HMAC. O erro de clone anterior foi superado pelo build seguinte; sua causa precisa ser confirmada nos registros SCM caso volte a ocorrer.
